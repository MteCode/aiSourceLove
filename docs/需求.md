## 一、角色

系统里有四种人，权限和入口都不同：

| 角色 | 是谁 | 从哪进 |
|---|---|---|
| **客户（会员）** | 来找对象的人 | 小程序，手机号注册 |
| **红娘** | 拉人、代录资料、牵线、拿分润 | 同一个小程序，身份升级后出现红娘专区 |
| **运营/审核** | 审档案、审照片、审红娘 | 后台管理端（Web） |
| **超管** | 配置字段、权限、套餐 | 后台管理端（Web） |

### 为什么不做成两个小程序

你提到「分为红娘版本和客户版本」。我的建议是**一个小程序、两套界面**，理由：

1. **审核成本翻倍** —— 两个小程序要两个 appid、两次类目审核、两份婚恋资质。资质本来就是当前最大的卡点。
2. **红娘本身也是用户** —— 她要看档案、看广场、看会员详情，这些页面和客户端完全一样。拆两个就得维护两份。
3. **身份会变** —— 客户申请成为红娘是产品设计里的路径（`pages/matchmaker/apply`）。两个小程序意味着他得换一个小程序用，体验断裂。

**做法**：登录后按角色决定首页和 tabBar。客户看到「广场/推荐/牵线/我的」，红娘看到「工作台/我的会员/牵线/我的」。同一个包，两套导航。

## 四、【重点】分享归属链路

你提的这条需求，后端已经全通，前端一行没写。

### 现状

```
后端  ✅ smsLogin(phone, code, ip, inviteMatchmakerId)
          → registerMember() 校验红娘存在且 ACTIVE
          → 写入 user.inviteMatchmakerId
      ✅ 建档案时自动转写成 profile.matchmakerId
          （profile.service.ts:77）

前端  ❌ 没有 onShareAppMessage —— 红娘根本分享不出去
      ❌ 登录时不传 inviteMatchmakerId
      ❌ 冷启动参数 scene/query 没有解析
```

### 要做的

1. **红娘侧生成分享**
   工作台加「分享给客户」按钮，`onShareAppMessage` 返回带自己 id 的路径：
   `/pages/login/index?mm=<matchmakerId>`
   同时支持生成小程序码（后端调微信接口，需 appid）。

2. **客户侧接收并暂存**
   小程序冷启动时 `App.onLaunch(options)` 拿 `options.query.mm`，存进本地。
   **必须暂存而不是立刻用**：用户点进来可能先逛半天才注册，中途还可能杀掉小程序重进。
   加过期时间（建议 7 天），避免半年前的分享还在生效。

3. **注册时带上**
   `authApi.smsLogin` 增加 `inviteMatchmakerId` 参数，注册成功后清除本地暂存。

4. **归属规则要定死**（这条得你拍板）
   - 已经有归属红娘的老客户，扫了别的红娘的码，算谁的？
     → 建议：**不改**，先到先得。否则会出现红娘互相撬客户。
   - 分享链接过期后注册，算谁的？
     → 建议：算无主，由运营在后台分配。

## 五、第一版范围（不含支付）

**做**：注册登录、分享归属、填资料、审核、广场、AI 推荐、看资料、解锁、牵线全流程、红娘工作台、分润查看。

**不做**：VIP 开通、订单、提现打款、微信一键登录。

**验收标准**：
1. 新客户扫红娘分享码 → 注册 → 填资料 → 提交审核 → 后台审核通过 → 出现在广场，且档案归属正确挂在该红娘名下。
2. 红娘登录 → 工作台看到这个新客户 → 发起牵线 → 双方同意 → 交换联系方式 → 标记见面 → 标记成功。
3. 全程无白屏、无报错、无死链接。

## 六、建议补充的功能

这几条不在原计划里，但我认为第一版就该有：

1. **举报 / 拉黑**（客户端）
   婚恋产品必备。没有举报入口，一旦出现骚扰或虚假资料，用户只能卸载。
   微信审核也会看这个。

2. **档案「已脱单」自我下架**（客户端）
   现在只有管理员能下架。成了的人没法自己关掉，会持续收到牵线打扰。

3. **红娘端「客户跟进备注」**
   红娘手上几十号人，靠记忆撮合不现实。一个自由文本备注字段能解决大部分问题。

4. **客服 / 联系红娘入口**（客户端）
   支付关闭后，「权益不足」的唯一出路是找红娘，但现在页面上没有任何地方能找到红娘的联系方式。
